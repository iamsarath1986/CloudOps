# Appendix A2 — Documentation Standards

The JD treats documentation as part of the job, not an afterthought: *"Publish and maintain high-quality documentation and a data catalogue for the technology area. Work within standard templates and documentation guidelines, including detailed designs, configuration details, support procedures, operations manuals, and deployment architecture."*

So documentation in Runway is **part of the engineering work**. A milestone is not complete when its documents are missing, the same way it is not complete when its tests fail.

---

## 1. Three rules

1. **Write it when it happens.** An incident timeline reconstructed afterwards is fiction. An ADR written after the build is a justification rather than a decision. Friday in the [weekly routine](../23-weekly-study-routine.md) is documentation day for this reason.
2. **Write for the reader who is not you.** A runbook is for someone at 3 a.m. who has never seen the system. A design document is for a reviewer who will challenge it. Test runbooks by having someone else (or you, a month later) follow them literally. Every stumble is a defect.
3. **Documentation lives with the code, in Git, reviewed by PR.** Diagrams are committed as source (Mermaid), not only as images. Nothing is maintained on a wiki that the pipeline cannot see.

## 3. Naming and metadata

- Sequential IDs that are never reused: `ADR-001`, `SDD-001`, `INC-001`, `PRB-001`, `CHG-001`.
- File names: `<ID>-<kebab-case-summary>.md`. Incident summaries describe the **symptom**, not the cause: `INC-014-checkout-latency-p95-6x.md`, not `INC-014-carrier-timeout.md`.
- Every document starts with a status line: `Status: Draft | Accepted | Superseded by ADR-0NN | Closed`, plus owner and date.
- Superseded ADRs are never deleted. They are marked superseded and link forward. The history of decisions is the evidence of judgement.
- `docs/adr/README.md` and `docs/incidents/README.md` hold an index table, updated by PR.

## 4. Templates

Copy these into `docs/templates/` in M00. Every later document uses them.

### 4.1 ADR — `docs/adr/ADR-NNN-title.md`

```markdown
# ADR-NNN — <decision as a short noun phrase>
Status: Proposed | Accepted | Superseded by ADR-0NN   ·   Date:   ·   Milestone: MNN

## Context
The problem, the constraints (cost, time, skills, JD requirement), and what forces a decision now.

## Options considered
### Option A — <name>
How it works · Pros · Cons · Cost · Operational burden
### Option B — <name>
...
### Option C — do nothing / defer

## Decision
What we chose, in one paragraph.

## Trade-offs accepted
What gets worse because of this choice, stated plainly.

## Consequences
What this enables, what it constrains, what follow-up work it creates.

## What would change my mind
Measurable signals that would trigger revisiting this (e.g. "> 20 services", "cost > $X/month").
```
*Rule:* the "Options considered" section should be longer than the "Decision" section. An ADR that dismisses its alternatives in one line is not an ADR.

### 4.2 Solution Design Document — `docs/solution-designs/SDD-NNN-title.md`

```markdown
# SDD-NNN — <solution name>
Status: · Author: · Reviewers: · Date: · Related ADRs:

## 1. Business context and requirements
Problem statement · stakeholders · functional requirements · out of scope
## 2. Non-functional requirements
| Attribute | Requirement | How it is met | How it is verified |
Availability (SLO) · Performance (p95) · Capacity (peak load, growth) · Continuity (RTO/RPO)
· Security (data classification, threats) · Reliability · Operability (on-call tier L1/L2) · Cost (monthly)
## 3. Architecture
Context diagram · container/component diagram · deployment diagram (Mermaid)
## 4. Key design decisions
Links to ADRs, one line each
## 5. Data
Data catalogue entries touched · classification · retention · residency · backup and RPO
## 6. Security design
Identity and access model · network exposure · secrets · threat model summary · controls
## 7. Operational design
Monitoring and alerts (tier, runbook) · dashboards · SLOs · support model · runbooks to be written
## 8. Standards conformance
| Standard (tagging, naming, network, policy, EA principle) | Conforms? | Exception + expiry |
## 9. Delivery plan
Phases · effort estimate · cost estimate (build + run) · risks and mitigations · dependencies
## 10. Lifecycle
Components with EOL dates · upgrade path · decommissioning
## 11. Open questions and approvals
```
This is the document the JD means by "solution definition, technical design" for project managers. Section 9 is where you practise giving a PM an honest estimate.

### 4.3 Runbook — `docs/runbooks/<alert-or-procedure>.md`

```markdown
# Runbook — <alert name or procedure>
Tier: L1 | L2   ·   Severity default: Sev3   ·   Owner:   ·   Last tested: <date, by whom>
Alert: <link to rule in platform/observability/>   ·   Dashboard: <link>

## What this alert means
One paragraph: the user-visible symptom, and why it matters.
## Impact if ignored
## Quick checks (L1 — safe, read-only, < 10 min)
1. <exact command or dashboard panel> — expected result — if not, go to step N
## Mitigation (L1 may perform)
Pre-approved standard changes only (e.g. scale out, rollback to previous digest). Exact steps.
## Escalate to L2 when
Explicit conditions.
## Diagnosis (L2)
Hypotheses in order of likelihood, each with the command that confirms or rejects it.
## Verification
The same signal that fired returns to normal for N minutes.
## Related
Past incidents · problem records · ADRs
```
*The test:* someone who is not you, at 3 a.m., follows it without asking a question. The `Last tested` line is mandatory.

### 4.4 Incident report — `docs/incidents/INC-NNN-symptom.md`

```markdown
# INC-NNN — <one-line symptom, not cause>
Severity: · Tier: L1/L2 · Detected: <ts> by <alert|user|me> · Mitigated: <ts> · Resolved: <ts>
Impact: <who, what, how long, how measured — SLO budget consumed>
Change-related: yes/no (CHG-NNN)

## Timeline (written live)
HH:MM  observed / did / concluded

## Detection
How we found out. If "I injected it so I knew", the monitoring failed — record that.
## Investigation
Blast radius first: which users, endpoints, environments, since when.
| # | Hypothesis | Evidence for | Evidence against | Verdict |
## Mitigation
What restored service, and when. Workarounds count.
## Root cause
The causal chain ("because X, Y happened"). Distinguish trigger, cause, contributing factors. "Human error" is never a root cause.
## Permanent fix
The change that removes the cause (link CHG / PR), or link to PRB-NNN if it belongs to problem management.
## Prevention
What stops this class of incident: detection improvement, guardrail, golden-path default, test.
## Follow-ups
| Action | Owner | Due | Status |
```
Its six headings are the **Detection → Investigation → Mitigation → Root Cause → Permanent Fix → Prevention** sequence used throughout the roadmap.

### 4.5 Postmortem / Post-Implementation Review — appended to the incident or change

```markdown
## Post-incident review (PIR) — held <date>
Blameless: describe systems and decisions, not people.
### What went well
### What went badly
### Where we got lucky
### Detection: time to detect, and what would have detected it sooner
### Response: time to mitigate; what slowed us down
### Decisions: which decisions were right given what we knew at the time
### Actions (prioritised, owned, dated)
```
Required for every Sev1/Sev2 and every **failed change** (a change that caused an incident or needed a rollback).

### 4.6 Problem record — `docs/problems/PRB-NNN-condition.md`

```markdown
# PRB-NNN — <underlying condition>
Status: Open | Known error | Resolved   ·   Owner:   ·   Opened:
Related incidents: INC-00x, INC-01y

## Problem statement
## Causal chain
## Contributing factors
## Why it recurred (why earlier fixes did not hold)
## Known error and workaround (while the permanent fix is pending)
## Permanent fix — options, cost, chosen option (CHG-NNN)
## Verification that it stopped recurring (period, signal)
```
Every fourth incident, stop and ask which incidents share a cause. That question is problem management.

### 4.7 Change record — `docs/changes/CHG-NNN-summary.md` (generated by the `change-record` workflow)

```markdown
# CHG-NNN — <summary>
Type: Standard | Normal | Emergency   ·   Risk: Low | Medium | High (score: N)
Requested by: · Implementer: · Approver: · PR: · Artefact digest / plan:
Environments: dev → prod   ·   Window: <start–end>   ·   Freeze calendar check: pass/fail

## Description and reason
## Risk assessment
Blast radius · reversibility · data impact · dependencies · tested in dev? (evidence link)
## Implementation plan
## Verification plan (signals and thresholds)
## Rollback plan (exact steps, expected time)
## Outcome
Successful | Failed (→ INC-NNN + PIR) | Rolled back   ·   Completed at:
```
*Change types:* **standard** is pre-approved, low-risk and repeatable (a digest promotion that passes all gates). **Normal** needs review and approval (infrastructure changes, schema migrations). **Emergency** is expedited to restore service, reviewed afterwards. Track the **change failure rate** monthly.

### 4.8 Data catalogue entry — `catalog/data/<dataset>.yaml`

```yaml
dataset: cargo-shipments
description: Shipment records, statuses and ETAs for internal cargo tracking
owner: team-cargo
steward: <person/role accountable for quality>
system: cargo-api
location:
  cloud: aws
  service: rds-postgresql
  account: workloads-prod
  region: <region>
  schema: public.shipments
classification: internal            # public | internal | confidential | restricted
contains_pii: false
residency: <region/country constraint, if any>
retention: 7y
backup:
  method: rds-automated + cross-region snapshot copy
  rpo: 5m
  last_restore_test: 2027-03-14
consumers: [eta-worker, insights-worker, runway-portal]
lineage:
  upstream: [carrier-sim]
  downstream: [shipment-exception summaries (insights-worker)]
access: role-based via IAM Identity Center group runway-cargo-readers
quality_checks: [not-null ETA for in-transit, referential integrity]
```
The portal renders these entries (M18). Adding a data store without an entry fails the golden-path policy check.

### 4.9 EOL register entry — `docs/lifecycle/eol-register.md`

```markdown
| Component | Current version | EOL / end of support | Replacement / target | Risk if missed | Plan (CHG) | Owner | Status |
|---|---|---|---|---|---|---|---|
| EKS | 1.xx | <date> | 1.yy | forced upgrade, unsupported | CHG-0NN, M14 | platform | Planned |
| ingress-nginx | n/a (local labs) | retired Mar 2026 | Gateway API | no security fixes | ADR-009 | platform | Done |
| PostgreSQL | 1x | <date> | 1y | extended-support charges | CHG-0NN | cargo | Open |
| Python base image | 3.1x | <date> | 3.1y | CVEs unpatched | CHG-0NN | cargo | Open |
| Terraform AWS provider | 5.x/6.x | — | next major | breaking changes | CHG-0NN | platform | Watching |
```
Review it every revision week. An EOL date that passes without a plan is an incident you scheduled for yourself.

### 4.10 Monthly operational review — `docs/operations/review-YYYY-MM.md`

```markdown
# Operational review — YYYY-MM
## Service levels
| Service | SLO | Attained | Error budget consumed | Notes |
## Incidents
Count by severity and tier · MTTA · MTTR · links
## Problems
Open problems and their age · known errors
## Changes
Count by type · change failure rate · emergency changes and why
## Capacity
Headroom vs plan · forecast breaches · quota requests
## Continuity
Backups verified · last restore test · DR drill status
## Cost
Spend vs budget per cloud · top three cost movers · anomalies · unit cost (per 1k requests, per AI summary)
## Lifecycle
EOL items due in the next 90 days
## Toil
Top three sources and what was automated
## Decisions and actions for next month
```
Twelve of these make a stronger artefact than any diagram in the repository. They are the direct, evidenced answer to the JD's service-level, capacity and continuity responsibilities.
